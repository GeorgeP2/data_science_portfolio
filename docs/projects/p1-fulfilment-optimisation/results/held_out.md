## Notes added after the run

The tables above are the run's output, unedited. One cell failed: **`peak_day` with optimal
routing**. Its 30-minute windows hold 90-297 orders, and at 1 s per window the exact router (about
15× slower per call than S-shape) didn't leave enough time:

- Savings costs every pair of orders before merging. It ran out of time doing so in 73 of 160
  windows (every window of 90+ orders) and returned single-order tours: a median 4.8× FCFS's
  distance, hence −304% on average.
- ALNS starts from the better of savings and FCFS under the same deadline, so on those windows it
  started from FCFS with almost no time left (7.6%). CP-SAT builds its pool with ALNS in half the
  budget and was starved the same way (5.3%).

With S-shape routing the same windows are fine (50% saved), and so is optimal routing on smaller
windows. The batching service isn't exposed: its runner returns FCFS whenever a solver's answer is
worse. Follow-ups, to be tested on development seeds rather than these held-out ones: savings
should return FCFS when it can't finish, and solvers should use a fast router for search and the
exact router only to evaluate the result on large windows.
